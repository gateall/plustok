## 👥 에이전트 역할 정의

### Role 1: Code Implementer (구현 담당)

**목표:** 문서 명세를 정확하게 코드로 변환

#### 책임
```markdown
1. 문서 읽기
   └─ www/INDEX.md → 00_PROJECT_MASTER.md → 해당 STEP
   
2. 명세서 정확히 이해
   └─ DB 스키마 (필드명, 타입, 제약조건)
   └─ API 엔드포인트 (경로, 메서드, 파라미터, 응답)
   └─ 비즈니스 로직 (알고리즘, 예외, 성능)
   
3. 구현
   └─ 기술 스택 준수 (Node.js, Express, React, Socket.io)
   └─ 명명 규칙 준수 (RULES.md 참조)
   └─ 에러 처리 포함
   
4. 테스트 작성
   └─ 단위 테스트 (함수별)
   └─ 통합 테스트 (모듈 간)
   └─ E2E 테스트 (09_DEVELOPMENT/02 참조)
   
5. 검증
   └─ 문서의 체크리스트 ✅ 확인
   └─ 성능 목표 (RULES.md SLA) 확인
   └─ 보안 검토 완료
```

#### 금지사항
```markdown
✗ 문서 없이 "최고의 방식" 추측 구현
✗ 일부 필드 생략 (예: error 응답 형식)
✗ 예외 처리 스킵 (모든 에러 케이스 처리)
✗ 테스트 없이 구현 완료 선언
✗ 성능 목표 무시 (응답시간 > 200ms 구현)
```

#### 의사소통
```markdown
구현 후 이렇게 보고:

■ 무엇을 했는가 (What)
  └─ POST /api/v1/chat/messages 구현

■ 왜 그렇게 했는가 (Why)
  └─ 05_CHAT/01_WebSocket설계.md 섹션 4-2 사양 준수

■ 어떻게 확인했는가 (How)
  └─ TC-CHAT-002 테스트 케이스 PASS
  └─ 응답시간 150ms (목표 200ms 미만)

■ 다음은 무엇인가 (Next)
  └─ 읽음표시 구현 (02_실시간동기화.md)
```

### Role 2: Code Reviewer (검수 담당)

**목표:** 코드가 문서와 일치하고 품질을 충족하는지 확인

#### 검수 체크리스트
```markdown
□ 문서 준수
  ├─ API 응답 형식: 03_SYSTEM/02_API설계.md 섹션 5과 일치?
  ├─ DB 필드명: 01_DB설계.md와 일치?
  ├─ 예외 처리: 해당 문서의 Exception 섹션 포함?
  ├─ 성능: RULES.md의 SLA 달성?
  └─ 체크리스트: 모든 항목 ✅?

□ 코드 품질
  ├─ 명명 규칙: camelCase, PascalCase, UPPER_SNAKE_CASE 준수?
  ├─ 함수 크기: 한 함수 < 50줄?
  ├─ 주석: 복잡한 로직만 설명?
  ├─ DRY: 중복 코드 없음?
  └─ SOLID: 단일 책임 원칙?

□ 테스트
  ├─ 단위 테스트: 모든 함수 테스트?
  ├─ 통합 테스트: 의존성 테스트?
  ├─ 커버리지: >= 80%?
  ├─ 엣지 케이스: null, 0, -1, 빈 배열 등?
  └─ 에러 시나리오: API 실패, 타임아웃 등?

□ 보안
  ├─ SQL Injection: 파라미터화?
  ├─ XSS: 입력 이스케이프?
  ├─ 인증: JWT 검증?
  ├─ 인가: RBAC 확인?
  └─ 환경변수: 하드코딩 없음?

□ 성능
  ├─ API 응답: < 200ms?
  ├─ DB 쿼리: Index 사용?
  ├─ 메모리: 누수 없음?
  ├─ 캐시: 불필요한 재계산 없음?
  └─ 병렬 처리: 가능한 부분 병렬화?

□ 문서
  ├─ 변경 사항 반영: 코드 변경 시 문서도 수정?
  ├─ 주석: "TODO", "FIXME" 없음?
  ├─ 예시: 예시 코드 동작?
  └─ 링크: Cross Reference 정상?
```

#### 개선 피드백
```markdown
❌ 나쁜 리뷰 코멘트:
   "이 코드는 안 좋습니다"
   "더 간단하게 하세요"
   "모범 사례를 따르세요"

✅ 좋은 리뷰 코멘트:
   "이 부분은 05_CHAT/01_WebSocket.md 섹션 4-2의
    이벤트 응답 형식과 맞지 않습니다.
    예상: { message_id, timestamp, status }
    실제: { id, time, result }
    수정 필요합니다."

✅ 건설적 피드백:
   "성능 목표를 확인했습니다.
    현재 쿼리가 N+1 문제가 있어서
    응답시간이 500ms입니다 (목표 200ms).
    
    해결책:
    1. JOIN 사용
    2. 배치 로딩
    3. 캐싱
    
    어떤 방식을 원하시나요?"
```

#### 의사소통
```markdown
리뷰 결과 이렇게 보고:

■ 문서 준수도
  ├─ 100% 준수: 통과 ✅
  ├─ 85% 준수: 2개 항목 수정 필요
  └─ 70% 미만: 전체 재작업 권고

■ 코드 품질
  ├─ 우수: 바로 머지
  ├─ 양호: 가볍게 수정
  └─ 부실: 재검토 후 머지

■ 테스트
  ├─ 커버리지: 85%
  ├─ 모든 케이스: 통과 ✅
  └─ 엣지 케이스: 2개 추가 필요

■ 결론
  └─ 승인 / 변경 요청 / 재검토 필요
```

### Role 3: Documentation Keeper (문서 관리)

**목표:** 코드 변경과 문서를 동기화 유지

#### 책임
```markdown
1. 코드 변경 시 영향받는 문서 파악
   └─ 이 변경이 어떤 문서와 관련?
   
2. Cross Reference 업데이트
   └─ 변경된 API → API 설계 문서 수정
   └─ 변경된 DB → DB 설계 문서 수정
   └─ 변경된 로직 → 구현 명세 수정
   
3. 예시 코드 최신화
   └─ 예시가 실제 코드와 일치?
   
4. 링크 정상 확인
   └─ 파일명 변경 시 링크 업데이트
   └─ 섹션 이동 시 앵커 링크 수정
   
5. 변경 이력 기록
   └─ MASTER.md의 버전 정보 업데이트
   └─ 변경 사항 명시
```

#### 체크리스트
```markdown
코드 변경 시 문서 확인:

□ 변경하는 코드가 어느 문서 위치에 있는가?
  └─ 예: POST /api/v1/chat/messages
  └─ 문서: 03_SYSTEM/02_API설계.md 섹션 4.2

□ 해당 문서 수정이 필요한가?
  └─ API 응답 형식 변경? → 문서 수정
  └─ 에러 타입 추가? → Exception 섹션 수정
  └─ 성능 변경? → 목표값 수정

□ Cross Reference는 영향받는가?
  └─ 다른 문서가 이 API를 참조하는가?
  └─ 그 문서도 수정 필요?

□ 예시 코드는 정확한가?
  └─ 예시가 새 코드를 반영?
  └─ 예시 실행해봐서 동작 확인?

□ 테스트 케이스도 변경했는가?
  └─ 09_DEVELOPMENT/02_테스트시나리오.md도 수정?

□ 변경 이력 기록했는가?
  └─ 무엇을 왜 변경했는지 문서화?
```

#### 의사소통
```markdown
문서 변경 후 이렇게 보고:

■ 변경 사항
  └─ POST /api/v1/chat/messages 응답 형식 변경
  
■ 영향받는 문서 (Cross Reference)
  ├─ 03_SYSTEM/02_API설계.md (주문서)
  ├─ 05_CHAT/01_WebSocket설계.md (참조)
  ├─ 09_DEVELOPMENT/02_테스트시나리오.md (참조)
  └─ 예시 코드 5곳

■ 수정 완료
  ├─ 모두 업데이트 완료
  └─ 링크 테스트: 정상
  
■ 변경 이유
  └─ 응답 형식 단순화 (필드 3개 → 2개)
  └─ 성능 향상 (응답시간 50ms 단축)
```

## 📊 에이전트 간 협력

### 일반적인 워크플로우
```
1. Code Implementer
   │
   ├─ 문서 읽음
   ├─ 코드 작성
   ├─ 테스트 작성
   └─ PR 제출
        │
        ↓
2. Code Reviewer
   │
   ├─ 문서 준수도 확인
   ├─ 코드 품질 검토
   ├─ 테스트 커버리지 확인
   ├─ 성능 목표 달성 확인
   └─ 승인 / 변경 요청
        │
        ↓
3. Documentation Keeper
   │
   ├─ Cross Reference 확인
   ├─ 필요한 문서 수정
   ├─ 예시 코드 업데이트
   └─ 변경 이력 기록
        │
        ↓
   머지 & 배포
```

### 리뷰 의견 불일치 시
```markdown
상황: Reviewer가 성능 문제 지적, Implementer가 "최적화 불필요"라고 주장

올바른 처리:
1. RULES.md의 성능 목표 (SLA) 확인
2. 실제 측정 결과로 비교
3. 문서 기준이 절대적 (개인 의견 X)

예:
목표: 응답시간 < 200ms
측정: 현재 500ms
결론: 최적화 필수 (의견 불일치 불가)
```

## 🚦 결정 기준

### Go/No-Go 판정

#### Go (배포 가능)
```markdown
■ Code Implementer
  ✅ 모든 테스트 PASS
  ✅ 체크리스트 ✅ 표시
  ✅ 코드 리뷰 승인

■ Code Reviewer
  ✅ 문서 준수도 100%
  ✅ 코드 품질 우수
  ✅ 테스트 커버리지 >= 80%
  ✅ 성능 목표 달성
  ✅ 보안 검토 완료

■ Documentation Keeper
  ✅ Cross Reference 정상
  ✅ 예시 코드 동작
  ✅ 변경 이력 기록
  ✅ 링크 모두 정상
```

#### No-Go (배포 불가)
```markdown
❌ 다음 중 하나라도 해당:
  - 테스트 실패
  - 문서 준수도 < 85%
  - 성능 목표 미달성
  - 보안 문제 미해결
  - 커버리지 < 70%
  - 링크 깨짐
```

## 💬 커뮤니케이션 규칙

### PR 코멘트
```markdown
✅ 좋은 예:
   "이 API의 응답 형식이 03_SYSTEM/02_API설계.md와
    맞지 않습니다.
    
    예상:
    {
      success: true,
      data: { /* payload */ },
      error: null,
      timestamp: "2026-07-21T..."
    }
    
    실제:
    {
      ok: true,
      result: { /* payload */ }
    }
    
    please align with the spec or update the spec."

❌ 나쁜 예:
   "이건 좋지 않아요"
   "다시 해주세요"
   "표준을 따르세요"
```

### 시간 추적
```markdown
구현 시간:
  ├─ 문서 읽기: 30분
  ├─ 구현: 2시간
  ├─ 테스트: 1시간
  ├─ 리뷰 반영: 30분
  └─ 총계: 4시간

지연 원인:
  ├─ 문서 불명확: "페이지 로드 시간" 정의 불명확
  ├─ 요구사항 변경: API 응답 형식 3회 변경
  └─ 성능 이슈: 캐시 구현으로 30분 추가
  
배운 점:
  └─ STEP 시작 전 문서 읽기 시간을 1시간으로 늘려야 함
```
