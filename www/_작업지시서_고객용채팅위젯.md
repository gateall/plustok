# 작업지시서: 고객용 실시간 채팅 위젯 (신규 기능) — 2026-07-22

**상태:** 설계 조사 완료 — 구현 필요 (규모 큼, 단계별 진행 권장)
**의도:** 지금은 `embed.js`(상담 신청 "폼")만 있고, 고객이 실시간으로 상담원과 채팅할 수 있는 화면이 없다. 이걸 새로 만든다.

---

## 1. 배경 (왜)

현재 두 시스템이 있다:
- **상담 신청 폼** (`embed/embed.js` → `consults` 테이블) — 폼 작성 → 나중에 전화/이메일로 회신받는 방식. 이미 동작 중.
- **실시간 채팅** (`/frontend/#/chat`) — **상담원 전용**. 고객이 볼 수 있는 화면이 없다.

목표: 고객도 웹사이트에 임베드된 위젯을 통해 **상담원과 실시간으로 채팅**할 수 있게 한다.

---

## 2. 조사 결과 — 이미 있는 것 / 없는 것

### 이미 있어서 재사용 가능한 것
- `chat-server`(Render, Socket.io)는 `role: 'agent' | 'admin' | 'operator' | 'customer'` 타입을 이미 인지하고 있음(`chat-server/src/middleware/auth.middleware.ts`) — `customer` role 자체는 설계에 이미 포함돼 있었음
- 소켓 인증은 **PHP가 서명한 JWT**를 `jwt.verify()`로 검증 (`chat-server/src/auth.ts`) — JWT 발급 방식만 맞으면 role 상관없이 통과
- 방 입장(`room:join`)은 PHP `GET /chats/{roomId}`를 호출해 접근권한을 재확인하는 구조(`chat-server/src/services/backend.client.ts:29-39` `assertRoomAccess`) — 소켓 서버 자체엔 role 하드코딩 없음
- 메시지 송수신 이벤트(`message:send/receive`)도 핸들러 레벨에서 role 제한이 하드코딩돼 있지 않음 (확인 필요하지만 room.handler.ts 기준으론 없음)

### 없어서 새로 만들어야 하는 것

| # | 항목 | 위치 | 상태 |
|---|------|------|------|
| 1 | **상담 접수(consult) 시 채팅방 자동 생성** ⚠️ 설계 변경 | `api/v1/consult.php` | 지금은 상담=리드일 뿐, `chat_rooms`와 연결 안 됨(반대로 채팅 종료 시 `consults`가 자동 생성되는 방향만 있음, `CrmCloseService`). **접수 시점에 `chat_rooms`도 같이 생성해서 처음부터 연결**하면, 아래 3번(별도 "채팅 시작" API)이 필요 없어짐 — `consult.php`가 이미 site 검증+rate limit+customer upsert를 다 하고 있으므로 그 흐름에 room 생성만 얹으면 됨 |
| 2 | 고객용 JWT 발급 | `JwtHelper`/`AuthService` 관련 | 없음. 지금 JWT는 전부 `agents` 테이블 기반. `customer_id`를 `sub`로, `role: 'customer'`로 발급하는 로직 필요. `consult.php` 응답(`consult_no`)과 함께 `roomId`+`accessToken`도 같이 반환하면 됨 |
| 3 | ~~고객이 채팅을 "시작"하는 별도 공개 API~~ | — | 1번으로 대체됨(불필요). 지금 `POST /chats/rooms`는 상담원 전용(`JwtMiddleware::requireRole(['agent','admin','operator'])`, `api/v1/router.php:76-79`)이라 별도 API가 있었다면 필요했겠지만, consult.php에 통합하면 생략 가능 |
| 4 | **방 접근권한 체크에 고객 본인 확인 로직 없음** ⚠️ 중요 | `includes/services/ChatService.php:244-256 requireRoomAccess()` | 지금은 `room['agent_id'] !== $agentId`만 체크함. `role==='customer'`일 때 `room['customer_id'] === $customerId`인지 체크하는 분기가 **반드시** 추가돼야 함 — 없으면 고객이 남의 채팅방에 못 들어가거나(과도한 차단), 혹은 반대로 잘못 짜면 남의 방에 들어갈 수 있음(보안 문제) |
| 5 | 고객용 채팅 화면(위젯 UI) | `embed/` 신규 (예: `embed/chat-widget.js`) | 전혀 없음. 접수 폼(`embed/embed.js`) 제출 완료 후 받은 `roomId`+`accessToken`으로 바로 이 위젯이 채팅 화면을 열어주는 흐름이 자연스러움 — 폼 제출 → 즉시 실시간 채팅 전환 |
| 6 | 스팸/어뷰징 방지 | `consult.php`에 이미 있음 | `rate_limit_ok()`(IP+site)가 이미 적용돼 있어 추가 작업 불필요. room 생성이 추가돼도 같은 요청 안에서 처리되므로 별도 방어 불필요 |

## 3. 제안 흐름 (설계 의도 — 세부 구현은 Cursor가 실제 스택에 맞게)

```
고객이 embed/embed.js 폼 작성 + 제출
  → POST /api/v1/consult.php (기존 로직 그대로: rate_limit_ok → site 검증 → customer upsert → consult insert)
      + [신규] chat_rooms 생성 (customer_id 연결, agent_id는 NULL='new' 상태, consult_id도 같이 연결해둘 것)
      + [신규] 고객용 JWT 발급 (sub=customer_id, role='customer', 짧은 TTL 권장 — 예: 세션당 2~4시간)
  → 응답: { consult_no, roomId, accessToken }  (기존 consult_no에 두 필드 추가)
  → 폼 제출 완료 화면에서 "상담원과 바로 채팅하기" 버튼 노출 (또는 자동 전환)
  → 클릭 시 embed/chat-widget.js가 accessToken으로 Socket.io 연결 (agent 쪽과 동일한 io(wsUrl, {auth:{token}}) 방식)
  → room:join, message:send/receive는 기존 로직 재사용
  → 상담원 쪽 `/frontend/#/chat`에 새 상담방이 "신규(new)" 상태로 나타나야 함 (상담원이 이미 보고 있는 목록에 실시간 반영되는지 확인 — 소켓 브로드캐스트 필요할 수 있음)
```

**참고**: 이렇게 하면 지금 있는 리드 폼(embed.js)과 실시간 채팅이 **하나의 흐름으로 합쳐진다** — 접수 즉시 채팅방이 있으므로, 고객이 폼만 내고 나가도 되고(리드), 이어서 바로 채팅해도 된다(라이브). 완전히 별개인 "채팅 전용 진입점"을 또 만들 필요가 없어짐.

## 4. 결정 필요 (구현 전 확인)

- [ ] 고객이 채팅 시작 시 **이름/연락처를 먼저 입력**받을지, 아니면 **바로 채팅창부터 열고** 대화 중에 연락처를 받을지 (UX 선택)
- [ ] 상담원이 배정 안 된(신규) 채팅방을 어떻게 인지하는지 — 실시간 알림(소켓 이벤트로 상담원 화면에 팝업/뱅크) 필요 여부
- [ ] 채팅 종료 시 기존 `CrmCloseService`(→ `consults` 자동 생성) 로직을 그대로 탈지 확인 — 이미 있는 로직이라 그대로 재사용 가능할 것으로 보임
- [ ] 상담 신청 폼(`embed.js`)과 이 채팅 위젯을 **사이트별로 둘 다 노출**할지, 하나만 고를지 (`sites` 테이블에 위젯 타입 컬럼 추가가 필요할 수 있음)

## 5. 완료 기준 (1차 MVP)

- [ ] `api/v1/consult.php`에 chat_room 생성 + 고객용 JWT 발급 로직 추가 (기존 rate limit/site 검증은 그대로 재사용)

- [ ] 상담원이 `/frontend/#/chat`에서 새로 들어온 고객 채팅을 실제로 보고 응답 가능한지 E2E 확인
- [ ] Rate limit/스팸 방지 동작 확인

## 6. 건드리지 않은 영역

- 기존 상담 신청 폼(`embed/embed.js`) — 그대로 유지, 병행 운영
- 상담원 채팅 화면(`/frontend/#/chat`) — 기존 로직 재사용, 구조 변경 최소화
