## 1. 배포 전략 개요

ACEP는 **이중 배포 경로(Dual-Path Deployment)** 를 지원한다.

```
┌─────────────────────────────────────────────────────────────┐
│                    ACEP Deployment Paths                     │
├──────────────────────────┬──────────────────────────────────┤
│  PATH A: Cafe24 (현재)    │  PATH B: Docker (향후 Full Stack) │
│  plustok.mycafe24.com    │  VPS / Cloud VM                  │
│  PHP 8.4 Shared Hosting  │  Nginx + PHP + Node + Redis       │
│  FTP/SFTP upload         │  docker compose up                 │
│  MariaDB (Cafe24)        │  acep-mariadb container            │
│  No Redis (V1.0)         │  acep-redis container              │
│  No Node WS (V1.0 poll)  │  acep-chat-server container      │
└──────────────────────────┴──────────────────────────────────┘
```

### 1.1 현재 운영 (Cafe24 PATH A)

| 항목 | 값 |
|------|-----|
| 호스트 | Cafe24 웹호스팅 (공유) |
| 도메인 | `plustok.mycafe24.com` |
| PHP | 8.4 |
| DB | Cafe24 MariaDB (phpMyAdmin) |
| 배포 | FTP/SFTP → document root `/www` |
| SSL | Cafe24 무료 SSL |
| Mail | `noreply@plustok.mycafe24.com` |

### 1.2 향후 Full Stack (Docker PATH B)

| 항목 | 값 |
|------|-----|
| 오케스트레이션 | Docker Compose 2.x |
| Edge | acep-nginx (TLS 1.3) |
| Backend | acep-backend (PHP 8.4-FPM) |
| Real-time | acep-chat-server (Node 20 + Socket.io) |
| Frontend | acep-static (React build) |
| Data | acep-mariadb, acep-redis |

### 1.3 배포 경로 선택 기준

| 조건 | 권장 경로 |
|------|-----------|
| PLUS톡 V2.0 PHP Admin/API만 배포 | PATH A Cafe24 |
| WebSocket + Redis + React SPA Full Stack | PATH B Docker |
| Alpha 내부 테스트 (단일 노드) | Docker dev compose |
| V1.0 MVP Cafe24 only | PATH A (현재) |

```
  3. api/v1/ (REST endpoints)
  4. admin/ (Admin UI)
  5. embed/ (customer widget)
  6. assets/ (CSS/JS — cache bust via query string)
  7. DB migration (phpMyAdmin — if schema change)

  3. acep-backend (wait for DB healthy)
  4. acep-chat-server
  5. acep-static (frontend build)
  6. acep-nginx (last — routes to all upstreams)
```

## 5. Zero-Downtime 전략

### 5.1 Cafe24 공유 호스팅 제약

| 제약 | 영향 | 완화 전략 |
|------|------|-----------|
| Blue-Green 불가 | 동시 2버전 운영 불가 | Maintenance window + delta FTP |
| Load Balancer 없음 | 단일 노드 | Atomic file replace, opcode cache clear |
| Node.js WS 미지원 | Real-time WS 별도 서버 | V1.0: polling; V1.5: WS VPS |
| Redis 미제공 | Rate limit 제한 | V1.0: DB/file; Docker: Redis |
| SSH 제한 | CLI 제한 | FTP + phpMyAdmin + Cafe24 panel |

### 5.2 Cafe24 최소 다운타임 배포 순서

```
T-24h: QA gate PASS ([08_TEST/04](../08_TEST/04_QA_릴리스_게이트.md))
T-1h:  Backup DB export + file snapshot
T-0:   Optional maintenance.html swap
T+0:   FTP upload changed files (delta manifest)
T+5m:  DB migration via phpMyAdmin (if schema change)
T+8m:  PHP opcode cache clear (panel or touch index.php)
T+10m: Smoke test SMK-01~07
T+12m: Remove maintenance.html
T+24h: Post-release monitoring + sign-off
```

### 5.3 Docker Zero-Downtime (Rolling Update)

| Strategy | Description | ACEP Service |

## 6. Rollback 아키텍처

### 6.1 Rollback Layers

```
Layer 1: Application Files  → FTP restore from snapshot
Layer 2: Database Schema     → Rollback SQL or full restore
Layer 3: Configuration       → config/ restore (preserve .env secrets)
Layer 4: Static Assets       → assets/ restore
Layer 5: Docker Images       → Previous image tag (e.g. v1.0.0-mvp)
```

### 6.2 Rollback Package 구성

| Artifact | Location | Retention | Owner |
|----------|----------|-----------|-------|
| File snapshot | Operator secure store | 3 releases | Operator |
| DB dump | Cafe24 backup + manual export | 7 days min | Operator |
| Git tag | v1.0.0-mvp etc. | Permanent | Dev Lead |
| Docker images | Registry tagged | 5 versions | DevOps |
| Deploy manifest | MD5 file list per release | Per release | Dev Lead |

### 6.3 Rollback Triggers

Ref: [08_TEST/04_QA_릴리스_게이트 §5](../08_TEST/04_QA_릴리스_게이트.md)

| Trigger | Severity | Auto Rollback |
|---------|----------|---------------|
| SMK-01~04 FAIL | S1/S2 | Yes |
| HTTP 5xx rate > 5% | S1 | Yes |
| DB migration fail | S1 | Restore backup |
| Security incident | S1 | Yes + incident response |
| AI all failed, chat OK | S3 | No — AI kill switch |
| Single admin page 404 | S4 | Hotfix, no full rollback |

### 6.4 Rollback Procedure (Cafe24)

1. Announce rollback to stakeholders
2. Restore file snapshot via FTP (overwrite changed files)
3. If DB changed: run rollback SQL OR restore phpMyAdmin dump
4. Clear PHP opcode cache
5. Run smoke SMK-01~04
6. Document incident in release notes

### 6.5 RTO / RPO

| Metric | Target | Cafe24 | Docker |
|--------|--------|--------|--------|
| RTO | 4 hours | FTP restore < 1h | Rolling rollback < 30m |
| RPO | 24 hours | Daily DB backup | Daily + binlog |

## 10. 배포 FAQ

### 10.1 Cafe24에서 WebSocket을 쓸 수 없나요?

공유 호스팅은 Node.js long-running process 미지원. V1.0은 polling, V1.5부터 VPS Docker Chat Server + wss 프록시.

### 10.2 staging과 production을 분리하려면?

현재 동일 호스트. V2.0부터 Docker staging VPS 또는 서브도메인 분리 권장.

### 10.3 config/database.php를 FTP로 올려도 되나요?

초기 설정·비밀번호 변경 시만. 일반 릴리스에서는 서버 파일 유지.

### 10.4 uploads/ 폴더가 배포时被 삭제되면?

절대 덮어쓰지 않음. 백업만 수행. EXCLUDE 목록 필수.

### 10.5 Zero-downtime이 불가능한 이유는?

Cafe24 Blue-Green 미지원. maintenance window 5~15분 목표.

### 10.6 Rollback은 얼마나 빨리 가능한가?

파일 스냅샷 기준 30분~1시간 (RTO 4h 이내).

### 10.7 AI key sandbox와 live 구분?

staging/sandbox key로 SMK-04, production은 live key. 혼용 금지.

### 10.8 PHP 8.4 미지원 시?

Cafe24 panel PHP 버전 확인. ACEP minimum PHP 8.4.

### 10.9 Docker 없이 ACEP MVP 가능?

가능. PATH A Cafe24 — PLUS톡 V2.0 확장 형태.

### 10.10 Health endpoint가 없을 때?

admin/dashboard.php 로드 + api/v1/consult.php POST 로 대체 smoke.

### 11.1 PII 배포 주의

상담 데이터(contacts, uploads)가 포함된 DB backup은 암호화 저장. Operator만 접근.

| Event | Log Location | Retention |
|-------|--------------|-----------|
| Admin login post-deploy | logs/ or DB audit | 90 days |
| Deploy timestamp | Release notes | Permanent |
| Rollback execution | Incident report | 1 year |
